## 实现与复跑

- DeepSeek 每次调用上限为两次请求。连接异常、超时和部分暂时性 HTTP 错误会在短暂等待后再试。限流响应若指定不超过 3 秒的数字等待值，按该值等待。超出本地等待范围时由调用方处理。输出截断时重发当前调用，要求精简 JSON 文字并保留所需字段和引用。认证失败直接返回。重试策略与错误分类参考 [DeepSeek 错误码](https://api-docs.deepseek.com/quick_start/error_codes/)和 [Chat Completions 对返回结果的说明](https://api-docs.deepseek.com/api/create-chat-completion/)。
- 自动重试用尽后，待执行节点仍由 LangGraph 检查点保存。用现有续跑入口恢复该节点，已经保存的步骤结果继续使用。
- 带任务编号的本地 DeepSeek 任务在 `runtime/traces/<task_id>.jsonl` 记录 Plan、检索、Resolve 和复核。每条包含节点、步骤 ID、状态、耗时和各次模型请求的结果。用量字段采用 API 返回值，输入估算单独保存。追踪记录不含任务正文、原始请求响应或凭据。评测 JSON 同时保存每题追踪。

```powershell
& '.\.venv\Scripts\python.exe' -X utf8 -m evaluation.recovery --mysql
& '.\.venv\Scripts\python.exe' -X utf8 -m evaluation.run --suite holdout
& '.\.venv\Scripts\python.exe' -X utf8 -m evaluation.run --suite all
```

真实模型、MySQL 和虚构台账配置见 [Agent 评测](README.md)。故障注入命令使用虚构合同和模拟 DeepSeek 响应，不消耗模型额度。省略 `--mysql` 可使用内存检查点。H09 单独执行时只需要本地 MySQL。

## 五个故障场景

| 注入事件 | 实测 | 已完成步骤的复核请求数 |
| --- | --- | ---: |
| 第二步首次请求超时 | 自动重试后完成 | 1 |
| 第二步首次请求返回 HTTP 429 | 按等待值自动重试后完成 | 1 |
| 第二步首次响应截断 | 发送精简输出要求后完成 | 1 |
| 第二步连续两次超时 | 停在第二步复核。重新连接 MySQL，调用续跑入口后完成。原计划与第一步结果保持一致。 | 1 |
| 第二步认证失败 | 返回错误，停在第二步复核。认证请求只发出一次。 | 1 |

故障注入针对模型传输层。检查点、节点调度和续跑入口使用实际项目代码，`--mysql` 运行使用本机真实检查点库。等待时间通过测试替身验证参数。
